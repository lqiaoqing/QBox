# ChatGPT 与 RTT Viewer 应用检索修复

用户报告搜索 chatgpt / rtt 无法直接找到应用。诊断确认 ChatGPT 的 Windows 应用注册存在，RTT Viewer 的实际 EXE 也存在且已进入 NTFS 索引。它们分别暴露应用来源遗漏和普通文件被目录/弱应用挤压的问题，不作为正常验收结果接受。

沿用既定应用来源补齐和排序实施范围，先修复可定位缺陷，不等待完整逆向。候选生成不写死应用名、查询词或路径，不导入用户历史。

1. 从 Windows Shell AppsFolder 只读枚举打包应用的显示名与 AUMID，使用稳定 AUMID 身份和 Shell 激活入口；仅补充具有包身份的应用，避免重复导入全部 Win32 开始菜单入口。失败时保留现有文件搜索并明确告知应用列表不可用。
2. NTFS 中匹配的便携 EXE 也作为可启动候选；仅有有效名称匹配时赋予应用优先级。WindowsApps 包目录中的 EXE 保留文件入口，由已注册的应用入口负责正常启动。
3. 匹配器分值为 1 的弱应用仍保留可查询，但不无条件压过强匹配目录和文件。这是 QBox 的来源修复策略，不能冒称已还原 Listary 的完整来源规则。
4. 核对注册应用身份、Shell 激活提交与失败时不记历史；验证不同启动动作不合并、原始扩展名和 DOS 别名覆盖、完整排序/有界收集一致。用真实快照和 Windows 当前应用注册回归 chatgpt/rtt 及已有五个案例，再发布单文件版本。

优先使用系统 Shell 注册与已有 NTFS 索引。直接依赖开始菜单 .lnk 无法覆盖当前 ChatGPT；直接打开 WindowsApps 下的 EXE不能替代包激活。常驻 USN、拼音及完整来源键仍按原计划继续。

跨来源回归进一步确认：只把所有 EXE 与已定义应用混在同一桶，会让系统工具挤掉 Neat Download Manager。最终来源次序为历史关联、已注册/快捷方式应用、直接 EXE、普通目录/文件；同一无关联应用来源层按匹配分值比较，不能以遍历先后占满首屏。这是 QBox 的应用来源修复策略，未宣称与未知的 Listary 来源完全等价。
