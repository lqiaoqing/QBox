# Listary 内存架构与 QBox 0.2.2 对照

结论：进一步缩减有空间，但本轮证据支持的是减少重复计算、明确查询状态生命周期、保持索引数据紧凑；不支持仅因 Listary 的驻留数字较小就改用 Rust/RocksDB，或通过裁剪工作集降低显示值。QBox 已完成的共享只读索引应保留。名称 UTF-16 去重仍是当前已量化的最大载荷空间，必须验证建库成本，才能承诺索引速度不减。

本轮为只读逆向与方案对照，未修改 QBox 产品实现、匹配排序、索引范围、USN 轮询频率或正式运行实例。原始分析和复现材料保留在忽略目录 `work/listary-memory-study-2026-11-15/`；仓库仅保留结论与脱敏证据清单，不包含第三方二进制或反编译源码。

## 研究对象与证据边界

本机读取的 Listary 主程序 FileVersion/ProductVersion 为 **6.3.5.94**，原生引擎自身版本为 0.3.1。这与仓库既有 7.1.0.47 优先级研究的工件不同，不能复用其地址或假定实现相同。

| 工件 | SHA-256 | 定位方式 |
|---|---|---|
| `Listary.exe` | `be2aec5c06d2731cb89a9799ffeeffdb063afe0da7f1dfcdeb33c6929e7b20d9` | .NET Framework 托管 CIL；MVID `64603b90-3193-c46d-c5ba-eeb31b6ca156` |
| `listary_engine.dll` | `1671b88533316e3b8fa2d1b4189ba31d77aa7174ac936e1ab2dff20b73c0882e` | AMD64 原生 PE，Rust/UniFFI 与 RocksDB 相关静态内容 |
| QBox 来源基线 | Git `071111077d9936a2555f9d4e657e6b52e36f9aa4` | 产品 0.2.2，可读取的源代码 |

证据分为：运行快照（当时实际加载模块和页状态）、静态调用链（代码存在并闭合，不代表本轮逐次执行过）、持久化参数（缓存目录已有文件，不代表实时内存值）、推断/待验证方案。静态字符串与导入名称只能作为定位线索；不能单独证明索引压缩方式、驻留布局或某个缓存正在使用。

托管全量自建 CIL 解码覆盖 9,064 个方法、0 解析错误；四份选定的 REA canonical Evidence 与之核对 11,439 个 token 指令锚、0 不符。原生 Ghidra 12.1.4 默认分析曾在 330 秒启动期限内未完成；随后按工具建议禁用 `Stack`、`Decompiler Switch Analysis`，完成缩小范围的分析和所选入口反编译。该 profile 的摘要记录 34,041 个已识别函数、11,985 个已定义字符串，不等于识别了全部函数/文本；未获得 PDB 符号，栈变量和 switch 自动恢复覆盖也受上述配置限制。未据此给出底层完整布局或全程序不存在某行为的结论。

## 内存数字如何对照

以下复用此前同机只读快照，未对任一目标强制 GC、裁剪工作集或注入代码。不是本轮重新执行的同负载 A/B：启动时间、历史操作、索引覆盖不同。

| 进程 | 私有驻留 | 总工作集 | 私有提交 |
|---|---:|---:|---:|
| Listary 主程序 | 97.0 MiB | 200.1 MiB | 696.9 MiB |
| QBox 0.2.2 GUI | 288.5 MiB | 863.3 MiB | 328.3 MiB |
| QBox 管理员后台 | 未获页查询权限 | 511.3 MiB | 41.7 MiB |

- 私有驻留表示当时独占且在物理内存中的页；私有提交表示需要系统提交额度支持的私有分配，不能与驻留视为同一指标。
- QBox GUI 的 C/D 只读索引映射驻留约 **424.61 MiB**；每卷当时各一份，未观察到旧基础映射重复。它可以与后台共享，两个进程工作集不能直接相加当独占物理成本。
- Listary 主进程实际加载 `listary_engine.DLL` 和 Framework64 CLR；已枚举服务和 HookHost 辅助进程，服务工作集约 4 MiB、两个 HookHost 各约 1 MiB。这个快照没有显示把数百 MiB 索引移到另一个巨大服务的证据。
- Listary 较低的驻留与较高的提交同时存在；本轮尚未将其差值归因到具体分配器、分页、冷数据或缓存，不能据此承诺把 QBox 降至 100 MiB。

## 已闭合的 Listary 当前调用链

### 当前后端是原生引擎，不能把保留的旧类当作正在使用的实现

启动路径为 `ListaryApp.Start` `0x06000b0e` IL251 → FileSearch 初始化 `0x0600187a` → 异步状态 `0x060018d3` IL57 → UniFFI engine 包装器 `0x060003c0`。独立窗口 Query setter `0x06000e4b` 可追到当前 FileSearch `0x06001893`，再到 native `search` 导入 `0x060002e7`。

原生导出提供 `search`（`0x180185690`）、`get_search_results`（`0x180183fd0`）、`open_session`（`0x180184330`）、`release_session`（`0x180184c60`）、`poll_indexer`（`0x180184640`）等入口。地址只适用于上表 DLL。

EXE 中仍有旧 `DiskSearchSessionCache`，但全 9,064 个方法的直接 CIL 引用未连接到当前启动/搜索主链。反射等间接调用未被排除，因此准确结论是“旧类不足以证明当前算法”，不是“旧类永远不运行”。

### 会话复用与结束释放值得借鉴

当前后端字段 `0x04000e44` 为 `Dictionary<SearchSessionToken,string>`。搜索 `0x06001893` IL52 查找已有 session id，未命中时创建 Guid 字符串并订阅 SessionDisposed。结束事件 `0x060018ac` IL17 从字典移除，随后经 `0x060018b1` IL69、包装器 `0x060003d3`、闭包 `0x0600043a` IL17 到 native `release_session` 导入 `0x060002e4`。

独立窗口 VM Dispose `0x06000e6e` IL46 和重置 `0x06000e85` IL6 通知结束。它证明了状态所有权和清理边界；不能仅凭 session id 复用就宣称原生内部支持查询前缀增量过滤，或知道候选缓存配额。

原生 `0x180184c60` 和 `0x180183fd0` 反编译可见 UniFFI future 状态与分配封装；`release_session` 不是在导出包装函数返回时就能保证所有缓存和分配器页立即归还系统的同步 RAM 承诺。所选 `snapshot.rs` 字符串交叉引用只连接到迭代/反序列化与错误处理片段，也不足以证明共享快照的驻留布局。

向内追踪到 `0x1801231e0` 时，反编译报告重叠指令、坏指令流及未恢复跳表，结果混入更大范围的控制流。本报告不采用这段伪代码推导内部缓存、所有权或分配器策略；原始输出仅留作复现限制，不能把“工具返回成功”视为语义恢复可靠。

### 摘要与结果行分开，但不是只缓存 100 行

当前 search 先产生包含 SessionId/TotalCount 的摘要（`0x060018af` IL1070/1083/1097）；UI 通过范围回调取结果（`0x06000ea9` IL64 → `0x06001894` → native `get_search_results`）。这样可以延迟创建未展示的行对象。

`LazyAsyncList<T>` 的两个常量含义已核对：10 是 **10 ms 取数合并**，100 是 **每批取数上限**。构造器 `0x06002008` IL56/61 仍为 TotalCount 分配引用槽数组；取回结果 `0x0600202c` IL208 保存到对应槽。未发现该集合按页淘汰的证据，因此不能称其总共只驻留 100 行。

QBox 当前 `SearchCollector` 已保留有限展示结果、单独计算总命中，并在显示时补路径。应保留这一优势，不为模仿分页引入全命中占位数组。

### 没有证据表明靠周期强制 GC 或工作集裁剪

主程序集唯一直接 `GC.Collect()` 位于 `0x06001583` IL122：创建、Show、Dispose 搜索窗口 VM 后清理；其唯一直接调用者是启动 `0x06000b0e` IL391。它属于启动预热清理，不能推导为每次隐藏或定时强制 GC。

托管方法/ImportMap 与原生 DLL 的完整 PE 导入表（241 个函数、无 delay imports）未发现直接工作集裁剪 API；额外字节扫描未发现所选 `EmptyWorkingSet`、`SetProcessWorkingSetSize`、`NtSetInformationProcess` 文本。此结论仅限这些静态范围，未排除其他模块或动态解析调用。

## 持久化与更新：可以确认什么

本机 Listary 缓存目录实际存在 RocksDB 的 CURRENT、MANIFEST、OPTIONS、SST 和 WAL 文件；原生 DLL 含对应 RocksDB 内容以及 `db/{builder,file_db,read_only,snapshot,transaction,writer,serialize}.rs`、NTFS MFT/volume monitor 等 Rust 源路径线索。仅路径名称不构成算法证明。

已存在的 `OPTIONS-002114` 声明 RocksDB 8.1.1；各相关 column family 参数包括 64 MiB `write_buffer_size`、`max_write_buffer_number=2`、Snappy、4 KiB block；DB 参数 `allow_mmap_reads=false`、`allow_mmap_writes=false`。这些是落盘设置：

- 64 MiB 是单个写缓冲参数，不能当作全进程内存上限，也不能简单乘 column family 数当当前实占。
- 磁盘 Snappy 不代表搜索热路径逐候选解压，`allow_mmap_reads=false` 也不能证明所有自定义索引都不使用映射。
- 还没有足够证据认定其名称池去重、ASCII 预筛结构、快照共享方式、block cache 配额或 Rust 分配器策略。因此不把这些猜测写成 QBox 的实现依据。

## 对当前方案的补充与优先顺序

| 顺序 | QBox 行动候选 | 预期收益与性能约束 |
|---|---|---|
| 1 | 内容未变化时复用查询结果；只检查点推进不触发重查 | 少分配、少 CPU；保持 USN 读取和索引应用，确认真实变化仍立即更新。收益未量化。 |
| 2 | 明确查询生命周期，处理前丢弃过期图标任务 | 减少后台无效工作和暂存对象；保留基础索引、热预筛与后台更新，验证再次唤出延迟。收益未量化。 |
| 3 | 完全相同的原始 UTF-16 名称共享文本 | 当前快照重复文本 **138.18 MiB**，索引载荷理论上由 424.61 降至约 286.4 MiB（新格式开销前）；不增加逐候选解码。哈希/建表/合并成本必须测。 |
| 4 | 仅极低频 ASCII 改为稀疏编号表 | 理论数组载荷约 **10.15 MiB**；高频字符仍用位图。阈值按查询耗时共同选择。 |
| 5 | 去除重复物理编号校验，后续研究顺序合并紧凑记录 | 降低建库/合并峰值及重复工作；保留完整发布前校验。全量对象物化改造应独立验证。 |

名称池与稀疏 ASCII 的数字来自 QBox 自身逐名称统计，不是从 Listary 压缩率外推，也不等于 GUI 私有驻留会等额下降。

具体代码对照：

- `MainWindow.xaml.cs:538–545` 因索引文件对象引用变化重查；而 `LiveIndexFile.cs:31–32` 与 `LiveVolumeIndex.cs:37–41,97` 对纯检查点推进已经复用底层数据。可独立跟踪“查询内容版本”。
- 应用目录每 30 秒刷新后，`MainWindow.xaml.cs:547,579–582` 未做内容等价判断就重查。必须比较动作、别名、注册应用及显示字段，不能只比条数。
- `MainWindow.xaml.cs:272–287` 重建行并请求图标；`ShellIconLoader.cs:12,20–22` 队列无容量/代次取消。当前仅在回调阶段忽略过期结果；可以在昂贵的 Shell 取图标前跳过过期任务。未测得积压量，不称其为已证实泄漏。
- Hide/Esc/Closing（`MainWindow.xaml.cs:131–132,338,590`）仅隐藏窗口；`SearchAsync:235–237` 未检查可见性，Monitor `:523–547`、目录刷新 `:582` 仍可能触发非空查询和图标任务，成功打开结果后 `:311,324` 也会隐藏重查。可以在隐藏时结束前台任务并标记结果待更新，Show 时按最新 generation 重查；后台 USN、Monitor、更新任务心跳和热预筛必须继续。QBox 只保留少量展示结果，收益主要是少重算和少临时分配，不是释放百万条常驻结果。
- `VolumeIndex.cs:461,466,468` 的 v1 校验要求名称文本顺序连续独占，`VolumeIndexStore.cs:79` 仅收 v1。名称共享需要显式新格式和 v1 兼容，保留名称记录、父目录、FRN、硬链接、DOS 名称及原始 UTF-16；禁止大小写折叠或 Unicode 归一化去重。
- `VolumeIndex.Create:105–110` 的物理编号 HashSet 与 `ValidatePhysicalRecords:493` 的最终排序检查重复；`NtfsIndexBuilder.Synchronize:72–77` 则把全基础快照导出为对象再合并。前者可小步减少冗余，后者是更大改造，不能混算为日常常驻收益。

暂不采用每次隐藏就强制 GC/EmptyWorkingSet、给逐候选匹配加全面解压、用二分查找替代 O(1) owner，或因存在原生引擎就重写整个桌面栈。它们尚无与用户“不降低索引速度”目标相符的收益证据。

## 不降速的实施门槛

本轮没有新产品实现，因此没有声称这些建议已经省内存或性能不减。后续每项原型与 0.2.2 对照：

1. 同一冻结输入，核对全部节点、每条 Name 元数据、原始 UTF-16 和身份等价；保留七类查询及中文、拼音、符号、硬链接、目录改名/删除回归，匹配排序不变。
2. 测初建、保存、加载、持续 USN 应用、增量日志、合并和切换；多轮交错基线/候选，记录中位数和尾延迟，区分噪声和可重复退化。不能以降并行、少文件、降更新频率换内存。
3. 真实物理卷 MFT 吞吐另测；此前 201,001 条记录/2,000 次改名缓存重放只能证明相应代码阶段，不能替代物理全盘扫描。
4. 对照自然空闲、连续输入、隐藏/唤出及合并期间的私有驻留、私有提交、托管存活、映射驻留与峰值；不强制 GC/裁剪来制造产品数字。隐藏优化还要单独通过首次唤出延迟与最新结果检查。
5. 旧 MemoryProbe 的查询证据为“总命中数 + 前九项全部 SearchHit 字段摘要”，不是全量命中集合逐项相等；格式变化增加上述全量结构流式等价检查，避免这一验收缺口。

证据 ID、工件身份与限制见 [脱敏清单](validation/listary-memory-study-2026-11-15.json)。本研究提供下一阶段决策依据，不自动授权匹配/排序大改或替换正式版本。
