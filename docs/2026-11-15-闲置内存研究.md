# QBox 隐藏闲置与再次唤出研究

结论：**值得继续的是快捷方式读取缓冲区复用，以及索引内容不变时复用入口清单。** 前者显著减少后台临时分配，后者减少反复扫描；本轮没有验证出能够大幅降低闲置驻留、同时保证唤出性能不变的方案。释放搜索预筛的重建代价明显，裁剪工作集也增加了再次唤出的耗时与缺页，均不建议默认采用。

本轮只做研究和隔离原型，产品源代码、正式实例、正式索引和版本发布均未修改。源代码基线为 `4a9f91526837afa2e02038d154dfa73fecea2190`，标准构建 0.2.3；没有切换全局名称共享试用策略。机器可读结果见 [脱敏测量清单](validation/idle-memory-study-2026-11-15.json)。

## 测量口径

- 同一冻结基础与增量：2,920,457 个基础文件、4,754,894 个基础名称、10,288 条增量记录，使用局部共享 v2 文件。它不是用户当时正在查看的实时数据副本状态。
- 每组是独立 STA 进程，使用真实 `MainWindow` 和复制自 `App.xaml` 的资源，独立空历史，跳过正式 Startup、全局热键、托盘和 USN 工作进程。真实窗口放在屏幕之外，实际索引监测继续运行。
- 九类输入 `Any`、`800Q`、`.code`、`nd`、`Tra`、`chatgpt`、`rtt`、`豆包`、`资料` 预热两遍，隐藏 65 秒，覆盖两次 30 秒应用目录刷新。所有候选保留应用元数据刷新，不通过暂停索引更新换取收益。
- 唤出计时从 `Window.Show` 到相同输入版本的首屏结果完成，并让 Dispatcher 再运行一次 ContextIdle。未覆盖物理热键、IME、实际屏幕合成完成或最后一个 Shell 图标回填；不能当作用户从按键到最终像素的完整延迟。
- 第一次唤出单列，随后六轮九类查询。总命中数与前九项完整 `SearchHit` 摘要跨所有组一致，共 576 条已记录唤出样本；未声称逐一比较所有命中行。
- 私有驻留、私有提交、总工作集分开记录。诊断器包含一个 8 MiB 原生缓冲区，各组相同；计数器按顺序采样，不是原子快照。GC 的 heap/committed 字段描述最近一次 GC，不能当作此刻精确存活对象总量。

机器没有进入独占基准模式，部分测试期间有标准 QBox 进程运行。没有制造真实系统内存压力，也未区分硬、软缺页。每个候选只有一次完整闲置周期，基线两次，不能据此宣称所有负载下零退化。初轮清单复用组的部分热查询与一次独立验证构建重叠，因此其热查询统计排除，使用后续 `inventory-clean` 复测。

## 闲置后的内存与首次唤出

以下内存均为隐藏 65 秒结束时的进程数值，单位 MiB；首次唤出统一查询 `nd`。

| 组别 | 私有驻留 | 私有提交 | 首次唤出 ms |
|---|---:|---:|---:|
| 当前实现，基线 A | 228.25 | 261.87 | 208.12 |
| 当前实现，基线 B | 223.64 | 256.54 | 296.73 |
| 复用快捷方式清单，干净复测 | 224.41 | 256.95 | 222.28 |
| 清单复用 + 批内缓冲区复用 | 223.81 | 256.91 | 230.47 |
| 清单复用 + 清图标缓存 | 224.72 | 257.34 | 233.68 |
| 清单复用 + Optimized GC 请求 | 222.73 | 255.44 | 240.59 |
| 清单复用 + Forced GC 请求，保留预筛 | 222.44 | 254.77 | 226.05 |
| 清单复用 + 释放预筛并完整回收 | 212.94 | 245.76 | **1,290.57** |
| 清单复用 + EmptyWorkingSet | **34.99** | 253.12 | **373.28** |

当前实现本身有自然回落：基线 A 从隐藏开始的 251.49 MiB 私有驻留、284.86 MiB 私有提交，回落到 228.25 / 261.87 MiB。它没有显式的完整闲置回收策略，但不能说隐藏之后内存完全不会下降。本轮也不能把这种自然回落归因于一个特定 GC 或工作集算法。

清单和缓冲区原型都没有显示出显著的驻留下降。它们的确定收益主要是减少后台扫描、分配与内存抖动，不能承诺将用户看到的约 300M 直接降至 100M。

## 值得尝试一：批内复用快捷方式读取缓冲区

[`ShellLinkReader.Read`](../src/QBox.Windows/Shortcuts/ShellLinkReader.cs) 每读取一个快捷方式，都创建三个容量为 32,768 字符的 `StringBuilder`，分别接收目标、参数和工作目录。仅这三个字符缓冲区每条原始容量就约 192 KiB。定期刷新不断重复这一分配。

独立原型仅将这三个缓冲区放到**一批元数据读取的专属 STA 实例**中，逐条 `Clear` 后复用。容量、COM 接口、身份校验、只读 Load、截断判断、动作字段与释放 COM 对象的边界全部保留；没有缩小参数缓冲区，也没有缓存过期动作。缓冲区不跨并发读取共享，批次结束即可回收。

先固定同一批 166 个候选，预热两轮，再交错对照八轮；发现候选的扫描不在此项计时中。每轮得到相同的 132 个动作、162 个有效快捷方式别名，`HasSameSearchContent` 对完整动作、参数、工作目录、标志、主入口及全部别名比较一致。

| 每批元数据读取 | 现有实现 | 批内复用 |
|---|---:|---:|
| 托管分配中位数 | 31.53 MiB | **0.56 MiB** |
| 用时中位数 | 120.79 ms | 119.01 ms |
| 用时范围 | 112.59–132.34 ms | 114.01–130.20 ms |

托管分配减少约 98.2%。用时相近，不将 1.78 ms 差异宣称为确定加速；此处不包含原生 COM 分配。

放入完整隐藏/唤出流程后，65 秒后台托管分配由“仅清单复用”的 **65.29 MiB 降至 3.33 MiB**，少约 61.96 MiB 的累计临时分配，**不是释放同样数量的常驻 RAM**。第一次唤出 230.47 ms，落在两次基线的波动范围；预筛和查询算法没有改变。

下一步适合将其作为最小实现单独交付，验证超长参数、空字段、前一次读取失败后继续读取、连续批次以及取消场景，避免缓冲区残留或跨线程共享。它减少与前台争用的分配，但本轮尚未完成产品级性能验收。

## 值得尝试二：复用快捷方式候选清单

[`MonitorIndexesAsync`](../src/QBox.Desktop/MainWindow.xaml.cs) 在隐藏期间也每 30 秒刷新应用目录；现有 [`ShortcutCatalog.Load`](../src/QBox.Windows/Shortcuts/ShortcutCatalog.cs) 会重新遍历基础和增量名称，寻找 `.lnk`。这会访问大索引，即使入口集合并没有变化。

原型首次发现后保留根目录范围内的候选，包括当前读取不到动作的入口。之后每 30 秒仍重新读取候选元数据和注册应用；仅当 `LiveVolumeIndex.HasSameSearchContent` 与根目录均未变化时复用候选清单。任何实际索引内容变化、基础换代、卷集合或根目录变化都保守退回完整发现，纯检查点推进则复用。

不要只依赖 `.lnk` 文件自身变化来失效：父目录改名、删除或 FRN 复用同样会改变入口路径。另需在正式实现中先完整构造新清单，成功后再发布，避免取消或异常把半成品变成有效缓存；失效后及时释放旧视图，防止继续持有旧基础映射。

65 秒内只发现一次，后续两次仅刷新元数据。15 秒至 65 秒区间的进程 CPU 时间，两个基线均约 1,328 ms，清单复用约 1,094 ms；同期累计分配从约 66 MiB 降至约 64 MiB。收益主要是省扫描，并未显示大幅省常驻内存。若真实卷频繁变化，保守失效会降低复用收益；本轮冻结数据不能代表该负载。

原型 15 项检查通过，覆盖检查点复用、快捷方式增删改名、祖先目录改名/删除/FRN 复用、基础换代、根目录和卷集合变化，以及读取失败恢复与参数改变。与完整重新发现的候选内容一致。匹配和排序规则没有改动。

## 不建议作为默认策略的候选

**释放搜索预筛。** 预筛数组载荷约 41.85 MiB，同时释放拼音预处理并回收后，托管估计从约 80.15 降至 27.84 MiB，私有提交立即仅减少约 9.08 MiB。65 秒结束时仍约 245.76 MiB；首次唤出需要重新扫描并构建辅助结构，耗时 1,290.57 ms，明显高于基线的 208–297 ms。保留这些热结构更符合工具软件的再次唤出目标。

**清图标缓存。** 75 项降为 0 后，私有驻留和提交基本不变，清理还会使下一轮重新读取图标。本轮没有证据支持将其作为主要内存优化。未来可以给明显增长的缓存设置合理上限，但目前已有 512 项上限，不需要为这批小缓存增加强制闲置清理。

**周期 GC。** `Optimized` 请求没有触发新的 Gen2 回收；改成 `Forced, blocking:false` 后确实触发回收，但私有提交从策略前约 255.50 MiB 到闲置结束约 254.77 MiB，收益很小。另做八次 GC 请求与唤出的竞争测试，每次确有新的 Gen2 回收，记录的累计 GC 暂停增量约 2.03–3.32 ms，唤出约 192–232 ms。这不是严格对齐的尾延迟 A/B，也不证明所有负载安全。微软说明 `Optimized` 可以不执行回收，而 `blocking:false` 也不是绝不阻塞的保证；本轮收益不足以引入周期强制回收。[Microsoft induced collections](https://learn.microsoft.com/dotnet/standard/garbage-collection/induced)

**EmptyWorkingSet。** 65 秒结束时私有驻留约 34.99 MiB，但私有提交仍约 253.12 MiB；首次唤出到结果完成新增 **122,071 次缺页**，耗时 373.28 ms。其他组首次唤出通常约 1,700–2,100 次缺页。没有区分硬/软缺页，不能把每次缺页当成磁盘读取；真实内存压力下的风险仍未覆盖。该 API 移出工作集的行为不等同于释放私有提交；它不是本轮目标下值得默认启用的省内存方案。[Microsoft EmptyWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-emptyworkingset)

## 性能结论的边界与实施顺序

六轮热查询的 `nd` 中位数 / 描述性 P95：基线 A 184.74 / 208.43 ms，基线 B 187.05 / 203.25 ms，清单复用 199.46 / 217.17 ms，缓冲区原型 197.13 / 223.61 ms。小样本、独立进程和系统负载存在波动，**当前数据不能被包装成“已经严格证明性能不减”**。首次唤出没有出现重建级别的明显退化，足以把这两项保留为候选；正式接入仍应交错复测，关注持续输入与后台刷新重叠时的中位数和尾延迟。

建议先实施缓冲区复用，再实施清单复用，分别记录差异，方便回退与定位。两者均不调整文件范围、名称匹配/排序、索引初建、基础合并或 USN 读取频率。**本轮没有重新测量索引吞吐，不能宣称已完成“不降低索引速度”的验收**；产品落地仍需跑已有索引初建、持续 USN 应用与合并对照，以及既有七类查询回归。

本轮没有重新逆向 Listary；沿用此前报告的限制：尚无证据将其观察到的闲置回落归因于周期强制 GC 或工作集裁剪。以上方案来自 QBox 代码与隔离实验，不将 Listary 的表面内存曲线当成机制证明。此前分析见 [Listary 内存架构对照](2026-11-15-Listary内存架构对照.md)。
