# Listary 优先级编码与注册后缀

本次补齐前一份计算报告中的两处未知量：设置类别到引擎类别的转换，以及文件后缀排序标记的配置来源。仅新增研究工具和证据，QBox 0.1.3 的匹配、排序、发布文件均未修改。

目标仍为本机 Listary 7.1.0.47，二进制 SHA-256 为 `f728593f86597b95d9ee79c03f8e7d313ca4c79a4bab8cf31f3768febeb8063f`。以下是选定区间的静态调用链及 Ghidra P-code 执行结果，不是原始源码，也不是运行中的 Listary 排名采样。

## 两次转换

设置层与原生引擎之间还有一层中间枚举。设置转换器 `0x1405e7c40` 将四个有符号字节转成中间值；`0x1416dda10` 再用常量 `0x010204` 的逐字节取值转成引擎类别。

| 设置含义 | 设置字节 | 中间枚举 | 引擎类别 |
|---|---:|---:|---:|
| 高 | 1 | 0 | 4 |
| 正常 | 0 | 1 | 2 |
| 不常用 | -1 | 2 | 1 |
| 不索引 | -2 | 3 | 0 |

设置转换器对其余 252 个字节进入不支持类别的错误分支。路径和名称适配器 `0x1405ef520 / 0x1405efb30` 调用此转换器；失败路径记录跳过该项，不能把任意字节截断成有效类别。

已核对的主要链路：

```text
设置路径/名称项
  -> 1405c4090：构造带中间类别的磁盘搜索设置
  -> 1405e82c0：构造路径、属性、名称、后缀优先级四个向量
  -> 140496a60：组装引擎配置
  -> 141596980 -> 1416dda10：转换四个向量的类别字节
  -> 141f03270 -> 原生规则编译及求值
```

`0x1405e82c0` 在相关开关为真时依次添加 SYSTEM（掩码 4）、HIDDEN（掩码 2）属性规则，中间枚举均为 2，即引擎“不常用”类别 1。该构造器的第四个“后缀优先级规则”向量为空；它与下文另行传入的“注册后缀集合”不是同一字段。

这使前一份报告中的数字有了明确含义：正常目录或带注册后缀标记的正常文件处于类别档位 2，其他正常文件处于档位 1；不常用档位为 0，高优先级档位为 3。目录覆盖和属性/名称合并的具体顺序仍按已经验证的合并公式，不能改成跨所有快捷栏分桶的统一移尾。

## 后缀标记来自 HKCR

`crates\listary-platform\src\executable_extensions.rs` 对应的实现 `0x1415bde70` 读取 `HKEY_CLASSES_ROOT`。已从 PE 导入表核对两次间接调用分别为 `RegQueryInfoKeyW`（IAT `0x143482fd8`）和 `RegEnumKeyExW`（IAT `0x143482fb8`）。

后续 `0x141682ac0 -> 0x141594af0 -> 0x141587f90` 只保留非空且以 `.` 开头的子键名，再调用字符串小写处理。该链路未检查关联的 ProgID、打开命令、PATHEXT 或是否为 PE 可执行文件。无效 UTF-16 名称会被跳过。

注册后缀提供器经 `0x1402a6bf0` 传给 `0x140496a60`，放在配置 `+0x90`；`0x141596980` 把它作为第五个向量传给 `0x1416dda10`，原样附到转换结果 `+0x60`，随后进入原生规则对象。查询时 `0x141b936c0` 以文件名称后缀查询该集合，目录不取得标记。

因此，内部源文件中的 executable 名称不能解释成“仅 .exe 提权”。本机只读注册表快照取得 1,035 个不同后缀，包含 `.exe`、`.lnk`、`.pdf`、`.txt`、`.zip`、`.png`、`.h`、`.pyc`、`.siproj`、`.code-workspace`。这些后缀文件也可能获得该排序标记；最终展示仍受优先级类别、匹配、上下文和 Launcher 分桶影响。

此数量来自本次直接读取 HKCR，不代表运行中的 Listary 缓存数量。当前快照全部为 ASCII；Rust 与 Python 的完整 Unicode 小写处理等价尚未验证。完整后缀清单仅留在被忽略的 `work/research`，提交内容只保存计数、示例及快照哈希。
